Univa 迁移效果差异

聚焦"哪些差异会改变最终生成产物的样子",而不是架构层面的工程改造。架构差异请看 结果对比 页。

只关注一种场景:左右两边都成功跑完同一段 user prompt 的标准 storyvideo 流水线(storyboard → 角色图 → 关键帧 → I2V → 拼接),最终拼出来的那条视频会有哪些可观察的差异。FW 没迁移的能力(音频、entity2video、video extension、video understanding 等)不在本页范围。

✓主流水线逐步对照(三方)

两边都成功跑完同一段 user prompt 时,storyvideo 主流水线每一步的对应关系。
左两列(UniVA 原版 vs FW univa 迁移版):已经全部对齐 ✓ —— 行为完全等价,只剩底层 T2I/I2V 模型(wavespeed vs fal)和 retry 机制是不可消除的差异(详见下方"差异点")。
右一列(FW 自家原生实现):跟 upstream UniVA 比较 —— 状态列只对 FW 自家实现而言。✓ 行为等价 / ⚠ 步骤存在但实现思路不同。
# 流水线步骤 UniVA 原版(univa/) FW univa 迁移版(agents/univa_*) FW 自家原生实现(StoryAgent / ScreenplayAgent / KeyFrameAgent / VideoAgent) native vs upstream
1 Storyboard 生成 LLM storyboard_gen.txt → 解析 JSON 出 characters / shots / style univa_storyboard 用同一份 storyboard_gen.txt ✓ 拆成两步:StoryAgent 先出 narrative blueprint(cast/locations/story_arc/scene_outline);ScreenplayAgent 再把 scene 展开成 shots,带 camera/framing/continuity_pack,粒度比 upstream 细一档 ⚠ 拆步
2 角色描述 LLM refine(每角色一次) refine_gen_prompt(media_type="character") + character_prompt_refine.txt univa_keyframe._refine_one_character + 同一份 prompt 文件,每角色并行 ✓ 没有"refine 已有描述"这一独立步骤。角色 prompt 由 KeyFrameAgent L1 global_anchors 阶段从 0 生成 prompt_summary(skeleton-first 模式,1 global LLM call 涵盖 character/location/prop) ⚠ 思路不同
3 角色参考图 T2I(每角色一次) text_to_image_generate(refined_char_description) materializer Phase 1 → ImageService.generate_image ✓ KeyFrameAgent.materializer Layer 1 对每个 global anchor(character/location/prop)调 ImageService.generate_image,并行 + 重试至多 10 轮 ✓
4 每镜关键帧 prompt(确定性 vs LLM) f"{setting} {plot} {static} {distance}, {angle}, {lens}" 确定性拼接 _compose_keyframe_prompt 用同一公式 ✓ 不是确定性。KeyFrameAgent 用 LLM 给每镜生成 prompt_summary —— skeleton-first 模式,1 个 global call + N 个 per-scene call 并行 ⚠ LLM 生成
5 关键帧 T2I(空镜,无角色出场) text_to_image_generate(keyframe_prompt) materializer Phase 2 → ImageService.generate_image ✓ KeyFrameAgent.materializer L3 阶段无 reference 时走 ImageService.generate_image 纯 T2I 分支 ✓
6 关键帧 I2I(带 reference) image_to_image_generate(keyframe_prompt, char_refs) —— 用角色图当 reference materializer Phase 2 → ImageService.edit_image(char_refs, prompt) ✓ reference 策略不同:KeyFrameAgent.materializer L3 默认走 edit-from-scene-loc —— 用场景 location anchor 当 reference 做 I2I,不用 character refs。可选 FW_ENABLE_PROP_PIPELINE 加 prop refs ⚠ ref 不同
7 每镜 I2V prompt(谁产生) 原样复用关键帧 prompt(等同步骤 4 的结果) univa_video._compose_video_prompt 与步骤 4 同公式 ✓ 不在 video 阶段产生。KeyFrameAgent LLM 在生成 keyframe prompt_summary 的同一次 LLM 调用里,顺手为每 shot 生成 video_motion_hint(1-3 句 subtle motion);VideoAgent 自身完全 LLM-free,只读这个字段 ⚠ 由上游 LLM 产生
8 每镜 I2V 视频生成(以关键帧为首帧) image_to_video_generate(keyframe, prompt) materializer → VideoService.generate_clip(keyframe, prompt) ✓ VideoAgent.materializer 读 L3 keyframe + video_motion_hint → VideoService.generate_clip ✓
9 合成最终视频(concat) merge_videos(video_segment_list) 直接 ffmpeg concat 一锅出 _merge_clips_ffmpeg 同样用 ffmpeg concat demuxer ✓ 分两层:先 VideoService.assemble_scene 把 shot clips 拼成 per-scene clip,再 VideoService.assemble_final 把 scene clips 拼成 final;合并算法下沉到 inference 层(底层仍然 ffmpeg 系) ✓

⚡影响最终视频的差异点(共 2 项)

每条都包含 ① UniVA 原版怎么做 ② FW 迁移版怎么做 ③ 对最终产物的具体影响。
设计目标:让 FW 迁移版本在主流水线行为上和 upstream 完全对齐,只剩"框架原本就有的横向能力"和"底层模型"两类无法消除的差异,方便 A/B 归因。
  1. 质量门槛与失败处理 FW 输出下限更高
    • UniVA 原版:storyvideo_gen 是顺序 for 循环,某 shot keyframe 失败 → logger.warning + skip;某 shot I2V 失败 → 同样跳过。没有"输出本身好不好"的判定,API 返回成功就采用,产物地板完全取决于模型当次发挥。
    • FW 迁移版:BaseAgent.run() 走 L1 结构校验(shot_videos 非空、video_prompt 非空)→ L3 资产 URI 校验,失败则 rework 重试最多 3 次。注:univa_video 的 L2 创意打分维度已置空(creative_dimensions = []),因为生成过程已经无 LLM,没有创意内容可评。
    • 对效果的影响:FW 输出最差产物的下限被抬高 —— shot 数对不上 storyboard、缺帧、video URI 落空 这类问题会自动触发重试;UniVA 一次过就采用,bad output 照单全收。代价是 FW 极端情况下消耗更多 token + 更长延迟。这是 FW 框架在 sub-agent 之外提供的"横向能力",不是 univa 主流水线本身的差别。
  2. 底层 T2I / I2V 模型本身 视觉风格直接差异
    • UniVA 原版:走 utils/wavespeed_api.py → wavespeed seedream-v4 / flux-kontext(T2I)、seedream_v4_edit(I2I)、seedance 等(I2V);模型档位由 config/mcp_tools_config/config.yaml 控制。
    • FW 迁移版:走 inference/generation/{image,video}_generators → fal.ai 系列;模型选择由 inference_runtime.yaml 管,univa_keyframe / univa_video 不知道也不关心后端是谁,可热切换。
    • 对效果的影响:这是两版输出最直观的差异来源。即便完全相同的 prompt,wavespeed 和 fal 出来的画面风格、细节质感、动作流畅度都不同。做盲测时必须先固定底层模型才能归因,否则唯一剩下的差异(质量门槛 retry)效果会被画面风格差异盖住。
