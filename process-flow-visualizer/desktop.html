Workspace 存储与读写

Workspace 是 Assistant 的本地运行时存储。新架构里只剩两份"事实文件"：global_memory.md 是 per-execution 的产物 ledger（每次 agent 跑出来的所有文件都在这里登记，附带 caption / scope），logs.jsonl 是 namespaced event 时间流（execution.* / artifact.* / workspace.*）。文件本身落在 artifacts/ 子树下，由 ArtifactWriter 一次性写入并自动注册到 global_memory。

① 数据流总览

用户 upload → ArtifactWriter 持久化 → GlobalMemory 注册 → 下游 agent 通过 InputResolver 拉数据 → 写 logs 留痕
user upload text / image / audio / video bytes
→persist_raw_upload
ArtifactWriter persist_execution_from_plan
artifact.* events
→register
global_memory.md per-execution ledger
+ per-file caption
artifacts/... JSON · PNG · MP4 · WAV
↑paths
InputResolver (LLM) match captions against
consumer's [label] slots
←get_captions_index
global_memory.md read side
Workspace 内一切产物都先经过 ArtifactWriter，落盘后由 GlobalMemory 注册带 caption / scope 的条目；下游 agent 启动时 InputResolver 把这些 caption 当成"自描述索引"喂给 LLM，让 LLM 决定哪些产物对应当前 agent 的哪个 [label] 槽。没有任何 agent 在 InputResolver 之外直接读 workspace 文件——这就是 caption-driven 的含义。

② · A' · entry 字段解释

取上面那份原文里的第 1 条（IntakeTextAgent）作为锚点，把每一项的含义、来源和消费方都标注出来。
{ "content": { // ← 这条 entry 的语义负载（content block，agent 在 generation 时填） "what": "natural-language brief from the user: \"A 30-second…\"", // ← agent 用一句话总结自己产出了什么；下游 agent 看 caption 就靠它 "why": "creative brief — elderly leather craftsman portrait short" // ← 这次产出的动机 / 创作理由；intake agent 根据 upload 的内容生成 }, "agent_id": "IntakeTextAgent", // ← 哪个 sub-agent 产出了这条 entry；新架构下也是 artifacts/<agent_id>/ 目录的 slug "task_id": "task_1_c6f46a7c", // ← 这条 entry 归属的 task（task stack 的 task ID）；upload 类 entry 的 task_id 为空 "execution_id": "exec_1_43fc0eee", // ← 本次 execution 的全局唯一 ID；同 task 的 (task_id, agent_id) 唯一对应一次跑 "created_at": "2026-04-07T09:37:58.337659+00:00" // ← UTC ISO 写入时间；director-facing brief 用它倒序排 }
字段 类型 由谁写 由谁读 / 消费方
content.what str producing sub-agent (在 ArtifactCaption 里填) InputResolver 的 LLM —— 用它做 caption-driven 的 [label] 匹配
content.why str producing sub-agent InputResolver 的 LLM；human 调试时也直接读
agent_id str ArtifactWriter._register_artifacts_callback（从 execution.agent_id 拿） find_by_producer / has_producer_run / get_global_memory_brief
task_id str ArtifactWriter（从 execution.task_id 拿；upload 类为空） get_captions_index 按 task_id 过滤；find_by_producer 用它做 dedup key
execution_id str storage.create_execution 生成（单调递增 + uuid suffix） global_memory_brief 行 ID；logs.jsonl 通过 execution_id join
created_at datetime (UTC ISO) GlobalMemory.register（datetime.now(UTC)） brief 倒序排序的 key
几个值得注意的点：
  • 每个 agent 的 descriptor 实现一个 build_captions(agent_id, output_dict)，在 agent 跑完之后从它的结构化输出里派生出一段自然语言 caption（比如 StoryAgent 的 "Story blueprint: N scene(s), M character(s), ..."）。这是 caption-driven 架构的关键：每个 agent 自己知道怎么"自我总结"给下游看。
  • execution_id 是这条 entry 唯一的 join key —— logs.jsonl 里同 execution_id 的事件都对应这一次 run。Director 想看一次 execution 的完整时间线就 grep 这个。
  • task_id 对 upload 类 entry 是空字符串（upload 在 task 创建之前发生），其他都填实际 task ID。这导致 get_captions_index(task_id=...) 必须显式包含 task_id == "" 的行，否则会漏掉 raw upload。

③ Workspace 内部模块

dynamic-task-stack/src/assistant/workspace/ · 由 Workspace.__init__ 装配

FileManager

file_manager.py

无状态字节读写：store_file_at_relative_path / read_binary_from_uri。不打日志、不维护索引——拒绝路径越权，仅此而已。Workspace 在它之上做 _touch。

GlobalMemory

global_memory.py

唯一的 semantic record：register / list_all / get_captions_index / get_by_paths / find_by_producer / has_producer_run / prune_by_paths。落盘到 global_memory.md（markdown 包 JSON entries 块），保留对老 artifact_registry.jsonl 的 backward-compat 读取。

LogManager

log_manager.py

append-only logs.jsonl。add_log(*, event, ...)——event 必填且只剩这一个分类轴。filter 按 event / agent_id / task_id / level / execution_id。老的 operation_type / resource_type / details.event_type 全部下线（仅在 _parse_log_line 里做了向前兼容）。

ArtifactWriter

artifact_writer.py

由 Workspace 注入回调（store_file / add_log / read_binary / register_artifacts / find_artifact_refs_for_producer / prune_global_memory_by_paths / delete_file_at_path）。负责 persist_execution_from_plan、hydrate_indexed_assets、collect_materialized_files，落盘后通过 register_artifacts 回写 GlobalMemory，并发出 artifact.persisted / artifact.snapshot_persisted / artifact.purged_for_producer 事件。由原 AssetManager 重命名而来——"asset" 一词留给 agent 内部的 MediaAsset / asset_dict。

InputResolver

input_resolver.py

懒加载：resolve_inputs_for_agent 调用时构造。读 global_memory.get_captions_index(task_id) + 拼 input_needs_description 里的 [label] (single|collection) 头 → LLM → { resolved_artifacts, selected_artifact_paths, rationale }。

与重构前的差异：① 旧的 MemoryManager 已删除（语义记录与 caption 不再分两份）；② 旧的 ArtifactRegistry 重命名为 GlobalMemory，并把 jsonl 换成 markdown 包 JSON 的格式；③ 旧的 AssetManager 重命名为 ArtifactWriter，所有 log 调用迁到 event=artifact.* 命名空间。

④ Assistant ↔ Workspace 读写边界

Workspace 是 Assistant 唯一对外的 facade（service.py 不直接 touch 任何 manager）
Assistant (service.py)
⇄
Workspace facade
⇄

READ — Workspace → Assistant

  • get_global_memory_brief(task_id, agent_id, limit) Director 轮询用：从 global_memory.md 投影出 {execution_id, agent_id, task_id, status, created_at} 的 slim view。HTTP 端点 GET /api/assistant/workspace/memory/brief。
  • resolve_inputs_for_agent(agent_id, task_id, input_needs_description, llm_client, model) 委托 InputResolver → LLM → { resolved_artifacts: dict[label, ResolvedArtifactEntry | list[ResolvedArtifactEntry]], selected_artifact_paths, rationale }。每个 ResolvedArtifactEntry 字段为 {caption, scope, path, mime, payload?}。
  • get_workspace_root_file_tree_text() workspace 全文件树（扁平视图），喂给 output persist plan LLM。
  • list_workspace_artifacts() 展平 global_memory 为 [{path, filename, mime, caption, scope, agent_id, task_id, execution_id, created_at}]。HTTP 端点 GET /api/assistant/workspace/files。
  • get_logs(*, event, agent_id, task_id, level, execution_id, limit) 多维过滤操作流。仅 keyword args；event 是唯一的分类轴。
  • hydrate_indexed_assets(assets) 委托 ArtifactWriter 把 _asset_index.json_uri 展开为可消费 payload。
  • collect_materialized_files(media_assets) 汇总 sub-agent 已物化的 MediaAsset，准备进入持久化计划。

WRITE — Assistant → Workspace

  • persist_raw_upload(file_content, mime, original_filename) 用户原始 upload 入口：写到 inputs/，登记到 global_memory.md（agent_id="user", task_id="", scope="raw_pending"），打 event=user.upload。
  • persist_execution_from_plan(execution, assignments, overwrite_existing) 主落盘入口。委托 ArtifactWriter 按 LLM 编排的 plan 批量落盘；overwrite 模式下先 _purge_all_for_producer 把同 (task, agent) 的旧文件 + 旧 ref 全部 wipe。返回 (persisted_paths, asset_index)。每次落盘自动通过 _register_artifacts_callback 把 ArtifactRef 追加到 GlobalMemory，并打 event=artifact.* 日志。
  • log_execution_started(execution) / log_execution_result(execution) 写一条 event=execution.started/.completed/.failed 日志，自动抽 retry_attempts + eval_summary。
  • store_file_at_relative_path(relative_path, file_content, filename) 底层字节落盘（FileManager wrapper）。不打日志——AssetWriter 在语义层一次性记录 artifact.*，避免双写。
重构后没有的写口：add_memory_entry / list_memory_entries / get_memory_brief（→ get_global_memory_brief）/ delete_file / 任何 memory/entries POST 路由 —— global_memory 的内容只能由 ArtifactWriter 在 persist 时自动注册，外部不能手写"语义条目"。
