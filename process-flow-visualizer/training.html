🔥 Training Pipeline (两阶段 LoRA)

① SFT

1,110 samples · 3 epochs · ~416 steps

学什么：从 goal 语义 → 28 种合法 chain 的路由映射；每条样本的 rationale 显式写 "No X because Y" 反 4 种 bias。

Loss：completion-only（prompt tokens=-100，assistant JSON cross-entropy）

lr=2e-5, bf16, batch=1, grad_accum=8

➜

② DPO

500 pairs · 1 epoch · β=0.1 · ~62 steps

学什么：在 SFT adapter 基础上，显式对 4 类常见 routing 错误做偏好纠偏——chosen 是 SFT 样本的正确 plan，rejected 注入一种 bias 的错误 plan + "找借口"式 rationale。

长度约束：chosen / rejected token 长度差 ≤ 10%（防止 DPO 偷学"长=对"）。

lr=5e-7, bf16, batch=1, grad_accum=8

➜

③ Adapter Artifacts

training/director/adapters_full/

adapters_full/sft/ — SFT 后 LoRA

adapters_full/dpo/ — SFT + DPO 后 LoRA（最终权重）

推理：infer.py --adapter adapters_full/dpo 加载 base + DPO adapter 跑 held-out eval。

Hardware：1× H200（80GB）就够——Qwen2.5-7B bf16 + LoRA r=32 只占 ~18GB，全 epoch ~30 分钟。 sbatch 见 training/director/train_full.sbatch，queue 用 non-reserved partition + eccv-2026 QoS。

① SFT — 输入 & 期望输出

📥 模型输入

两条 chat messages：[system, user]

system：planner prompt + 19 个 agent 的 catalog（~2300 tokens） user ：user_goal 一句话（例："Make a rebirth-revenge mini-drama about a woman framed by her best friend..."）

📤 期望输出

一段合法 JSON 字符串，schema 固定：

{ "rationale": "User asks for pure creation of... No XxxAgent because...", "plan": [ { "agent_id": "IntakeTextAgent", "intent": "..." }, { "agent_id": "StoryAgent", "intent": "..." }, ... ] }

下面 "🔍 两条代表性 SFT 样本" 里能看到真实 user/assistant 对的完整内容。

② DPO — 输入 & 期望输出 & Loss

📥 模型输入

三元组 (prompt, chosen, rejected)——同一个 prompt 配 一好一坏两个 assistant 答复：

{ "prompt" : [ system + user ] # 跟 SFT 同款 "chosen" : [{ role: "assistant", content: 正确 JSON }] # 从 SFT 样本拷来 "rejected": [{ role: "assistant", content: 注入 bias 后的 JSON }] # 4 类 bias 之一：VA / Ambience / Compositor / missing_IntakeText }
约束：chosen / rejected 的 token 数差 ≤ 10%，否则 DPO 会偷学 "长 = 对" 这个 shortcut。

📤 期望输出

DPO 不生成新 token——它要求模型对同一 prompt 下的两个 completion 打出对比鲜明的 log-prob： chosen 的相对 log-prob 涨，rejected 的相对 log-prob 跌。 训完 adapters_full/dpo/ 就是带着这个偏好的 LoRA。部署时 推理接口跟 SFT 一模一样（base + LoRA + 自回归生成 JSON）。

🧮 Loss 公式

Δchosen = log πθ(yw|x) − log πref(yw|x)
Δrejected = log πθ(yl|x) − log πref(yl|x)

LDPO = − log σ( β · (Δchosen − Δrejected) )

πθ = 可训 policy（base + SFT LoRA，LoRA 可更新）； πref = 冻结参考（同 base，LoRA 旁路）。 直觉：policy 把 chosen 的相对概率提上来、rejected 压下去，括号里为正，sigmoid → 1，loss → 0；反过来 loss 大。 β=0.1 是 KL 锁，防止 policy 跑得离 ref 太远。

📝 每条 SFT 样本的三层变化（不是只学 chain 结构）

① goal: 题材 × 设定 × 角色 × 语言

光 Creative 核心 150 条就覆盖 13+ 大类：cultivation / martial-arts / CEO / rebirth / palace / cyberpunk / horror / thriller / sports / rom-com / historical / slice-of-life / mystery。每条 user_goal 再细分情节、角色、地点。

例："Make a cultivation-fantasy animated drama about a sect junior who discovers the revered elder is the demon the sect was founded to purge"

② rationale: 显式反 4 种 bias

每条都写 "No VideoAnalysisAgent because..." / "No AmbienceAgent because..." / "No CompositorAgent because..." 对应位置补 why-not。

这是 routing 判断的关键监督信号——不只是链模式，而是每条 agent 该不该出现的 reasoning trace。

③ intent per agent: grounded 到当前 goal

每步 8–25 词，必须引用当前 goal 的具体情节 / 角色 / 物件，不是模板（eval 会抓 "step for MusicAgent" 这种模板化输出扣分）。

例："Generate keyframes for the killing-formation's seven layers and the swordsman's progression"

⚖️ DPO 偏好对 — 4 类 routing bias 纠偏（每类 125 对）

DPO rejected 是程序化从 SFT chosen 注入 bias 生成的。注入逻辑在 training/director/gen_dpo.py，每类 125 对。chosen/rejected token 长度差严格 ≤ 10% （validate.py check #3 拦）。

isolation 的实际软肋：normalize 只去空白+标点，同义改写会漏过。我在生成时手动避开 eval 的 15 个 creative 关键 hook（cr_01 到 cr_15），但规则化防线仅做兜底。DPO rejected 是从 SFT 里采样后再注入 bias，所以如果 SFT 通过 isolation，DPO 也通过。

🎯 Evaluation Baseline

训练好的 LoRA 用 infer.py --adapter adapters_full/dpo 跑 evals/director_routing/eval_cases.json（100 条 held-out）。同一 eval 脚本跑了 Gemini 2.5-flash 四个档位做对比：

档位Scaffoldchain accstep acc
baselinefewshots + topology 全开88.0%92.5%
no_topology只 fewshots，没 topology hint79.0%88.2%
no_few_shots只 topology hint，没 fewshots72.0%82.6%
no_few_shots_no_topology裸 Gemini，支架全关55.0%74.3%

对标应该是 55%（裸 Gemini），不是 88%——88% 是 Gemini flash + fewshot + descriptor 补丁全套"支架堆"的成绩，而 LoRA 训练的唯一目的就是把这些支架烘进权重里，跟 88% 比是拿带支架的成绩当新 baseline，苹果对橙子。 LoRA 要证明有用，就得在 不挂 fewshot / topology hint 的条件下把 55% 拉起来； 目标：追到 85%+（即 95%+ 的支架效果内化），同时吃掉 Gemini API 的成本和延迟。
