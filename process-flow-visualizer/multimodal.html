🛠️ 工作机制概述

① 多模态输入是怎么处理的

  1. 2 步 ingestion：用户上传走 POST /api/workspace/upload → workspace.persist_raw_upload 把文件写到 inputs/，注册一个 placeholder caption（scope=raw_pending，what="raw user upload, awaiting semantic analysis"）。这一步只存字节，不做任何理解。
  2. Intake* agent 提升语义：Director 根据 mime 调对应的 IntakeText / IntakeImage / IntakeVideo / IntakeAudio。
    • IntakeText：短文本（≤800 char）静态包装，无 LLM 调用；长文本调一次 LLM 摘要。
    • IntakeImage：构造多模态消息 → vision LLM (Gemini 2.5 Flash) → ≤150 char 视觉描述。
    产出一个 caption-rich artifact（scope=global，what 含具体语义）。
  3. InputResolver 语义匹配：每个下游 agent 在 input_needs_description 里声明 [label] (single|collection) 头。InputResolver 把整个 artifact_registry 的 caption 索引和 label 描述都喂给一个 LLM，让它做自然语言匹配，挑出每个 label 应该消费的 artifact。
  4. 没有硬路由：不按 mime、不按文件名、不按目录路径决定谁吃哪个产物。生产者写 caption，消费者写 label，匹配靠 LLM 读懂语义。新增一种 modality 只需要加一个 IntakeXxxAgent + 在下游 agent 的 label 描述里加一句。

② 多轮任务 / overwrite 是怎么处理的

  1. (task_id, agent_id) 唯一：每对 (task_id, agent_id) 在 workspace 里只有一份 active 输出。同一个 task 里 agent 重跑时，新输出替换旧输出。
  2. 怎么检测到是重跑：完全无状态机 / 无计数器 / 无时间戳。AssistantService.execute_agent_for_task 入口处直接调 artifact_registry.has_producer_run(task_id, agent_id) —— 扫一遍 append-only registry，看有没有任何 entry 的 (task_id, agent_id) 跟当前请求的相等。命中 → auto_overwrite = True，没命中 → 走全新写入路径。"事实即检测"：registry 里有没有同名产物就是唯一判据。
  3. prune-on-rerun：检测到是重跑后，overwrite_existing=True 一路传到 asset_manager.persist_execution_from_plan，写新输出前先调 artifact_registry.prune_by_producer(task_id, agent_id)，同时删掉文件 + registry entries。所以磁盘上看不到历史版本。
  4. 为什么不保留历史：因为下游 agent 全靠 InputResolver 的 caption 语义匹配。如果新旧两份产出都在 registry 里，LLM 可能挑错版本，或者两份都拿过去吃，下游就看到不一致的上游。"只有一份当前事实" 是 caption-driven 路由能稳定工作的前提。
  5. 用户上传永远保留：raw upload 注册时是 agent_id="user", task_id=""，跟任何 content agent 的 (task_id, agent_id) 元组都不相交，所以永远不会被 prune。重跑只删 AI 生成物，用户的原始素材始终保留在 inputs/ 和 registry 里。
  6. 实例：本页 e2e2 v1 video 和 e2e4 phase 1 video 看不到的原因——它们就是被 v2 / phase 2 重跑触发的 prune 干掉的。但 e2e2 的 v1 文本上传和 e2e4 的 phase 1 文本上传都还在 inputs/（因为是用户素材）。
