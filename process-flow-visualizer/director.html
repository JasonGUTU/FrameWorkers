💡 核心 insight（修订版）

LLM 更信任 descriptor 里的"事实"，不信任 prompt 里的"规则"——这条结论 baseline → v2 的实验仍然成立：把 "AFTER XXX, BEFORE YYY" 写进 descriptor 后，30+ 个 Step-1 跳过 IntakeText 的错误确实修好了。

但这把利剑两面开刃：catalog 里的硬绑定救了"线性 standard chain"那批失败，又造成了**新一类**失败——所有需要 子集 / 分支 / 替换 的任务（只要 BGM 不要 trio、VoiceClone 替代 Narration、后期链不需要 Compositor、bilingual subtitle 顺序反转）都被 catalog 里"REQUIRE / ALWAYS / standard chain" 类的措辞**反向锁死**。16/19 个 descriptor 都在硬编码邻居 agent 名字这件事，本身就违反了根 CLAUDE.md 第一条 "Sub-agent 解耦：每个 agent 自包含...互不依赖"。

🧪 PoC 实验：全 catalog 软绑定（poc_full_soft）

实验思路："catalog 硬绑定是所有失败的根因吗？"——全部 22 个 descriptor 的 catalog_entry 统一改为 capability card（描述 Purpose + Input/Output **数据类型**，不点名其他 agent，不写 "AFTER / BEFORE / REQUIRE all"），看是否能在修好硬绑定失败的同时保住现有能力。
GT 同时做了 2 条歧义修正：transcribe_02 / trans_trans_03 在 user_goal 里补了 "audio file" / "audio recording"——因为"podcast"、"interview"这种词在没有 modality 提示的情况下 LLM 确实无法判断是音频还是视频。

🔍 这次实验学到的

1. catalog 硬绑定不是"纯负债"，它是 LLM 路由的主要 scaffolding。 22 个 descriptor 里那些 "AFTER StoryAgent, BEFORE KeyFrameAgent" 的文字看似违反解耦原则，但对 LLM 来说是**可操作的全局流水线地图**。完全去掉之后 LLM 没了锚点，即使我在软绑定版本里写了冗长的"Run me when..."场景描述，LLM 还是会**漏跑必要步骤**（比如 cr_* 的 trio 只跑一个）或**错跑不必要步骤**（edge_01 空输入跑全流程）。

2. 硬绑定真正的病是"REQUIRE all / ALWAYS / standard chain"这种绝对量词，不是"点名其他 agent"本身。 点名提供 scaffolding 是好的；问题出在措辞里没留出口——写 "REQUIRE all three" 就让 LLM 觉得缺一不可；写 "typically runs after X, but skip if user task doesn't need it" 就既有 scaffolding 又有弹性。

3. 所以下一步应该是"精修硬绑定"，不是"全面软绑定"。 具体：保留 "AFTER X / BEFORE Y" 的顺序线索，只把 "REQUIRE all / always / standard chain / MANDATORY" 这种绝对量词替换成 "typically / when user asks for / optional"。这个在 poc_trio 那版只改 4 个 trio descriptor 的实验里其实已经能部分验证——可惜那次跑挂在最后一个 case 上，JSON 没写成。

4. 结论：我的最初假说 "catalog 硬绑定是根因" 半对半错——对于 complex_04 / bilingual_01 这种边界 case 是真的，对于 cr_* 这种主流链是错的。正确诊断是"绝对量词 + 无出口措辞是根因"。

🎯 Director 的 soft hint 应该怎么写

当前 director_agent/prompts.py 的 ROUTING_PIPELINE_STEP_SYSTEM 只有一条全局硬规则（"Intake first"），一条反规则（"Do NOT assume a fixed pipeline order"），没有任何"典型链模板"。下面是建议新增的 soft-hint 块——把本来散在 22 个 descriptor 里"我在哪一段"的 scaffolding 集中搬到 director 一个地方，每个 agent 的 catalog_entry 就可以纯粹只讲 Purpose + I/O 了。

📝 增补到 ROUTING_PIPELINE_STEP_SYSTEM 末尾（soft hint，不是硬规则）
- **Typical pipeline shapes (SOFT HINTS — deviate whenever user intent differs)**:

  1) Creative film production (brief → finished film):
     IntakeText → (BriefEnricher if images) → Story → Screenplay
     → KeyFrame → Video
     → subset of {Narration, Music, Ambience} driven by user's explicit ask
     → AudioMix (if any audio above ran)
     → (Subtitle if requested) → Compositor → done

  2) Existing-video post-edit:
     IntakeText → IntakeVideo
     → one of {StyleTransfer | Inpaint | VideoExtend | Highlight}
     → (Transcription+Subtitle if user wants subtitles on result)
     → done OR Compositor (only if final combines multiple tracks)

  3) Audio workflow (no video creation):
     IntakeText → IntakeAudio → Transcription
     → (Translation if user wants translated transcript / foreign subs)
     → (Subtitle if user wants subtitle file output)
     → done

  4) Voice-clone creative (user-supplied voice → full film):
     IntakeText → IntakeAudio (voice sample) → VoiceClone
     → replaces generic Narration in shape (1) above

  5) Transcribe-translate-subtitle on existing video:
     IntakeText → IntakeVideo → Transcription → Translation → Subtitle → done

- These shapes are **maps, not contracts**. When the user asks for something
  outside these shapes (e.g. "只要 BGM 合成", "bilingual subtitles"),
  compose the minimum subset of agents that satisfies user intent.
  Prefer doing LESS than the template when the user's ask is narrower.

这么写的三点考虑：

  • Maps, not contracts —— 明确标注 "SOFT HINTS — deviate whenever user intent differs"，从全局一次性给出 LLM "通常链是这样" 的锚点，又告诉它可以偏离。
  • 把出口写进模板本身 —— shape (1) 的 trio 那一行写 "subset of {...} driven by user's explicit ask"，同一行里同时给出 scaffolding 和弹性。
  • 最后一行 "Prefer doing LESS than the template" —— 专门对付 v2 硬绑定里"倾向补齐 standard chain" 的惯性。

更新：上面这个 soft-hint 块已经真的加到 director_agent/prompts.py 的 ROUTING_PIPELINE_STEP_SYSTEM 末尾了，并在当前"全软绑定 catalog"状态下跑了 poc_softhint eval——结果见下。

🔍 从两次实验综合得出的最终诊断

1. Scaffolding 不可搬——把"典型链模板"从分散的 catalog 搬到集中的 director prompt，LLM 几乎没有用上。可能的机制：
  • 局部性效应（locality）：每次路由决策时，LLM 更信任"我手上正在考虑这个 agent，它自己说自己在 X 之后跑"，而不是"我之前看到 system prompt 里有一张模板图"。
  • 注意力预算：system prompt 里的 pipeline templates 块要在每次 routing 调用里和 user goal、global_memory、23 个 agent 的 catalog 一起竞争——容易被稀释。而每个 agent 自己 catalog 里的 "AFTER X / BEFORE Y" 在 "当前候选 agent 是 X" 时会被优先关注。
  • Gemini 2.5 Flash 特性：可能本身对中长 system prompt 里的抽象规则不敏感，对具体 agent 描述里的具体线索更敏感——这是经验观察，不是定论。
2. 正确方向不是 "soft catalog + soft hint"，是 "精修硬 catalog"——保留 "AFTER X / BEFORE Y" 的点名 scaffolding（这是有价值的），只替换绝对量词（"REQUIRE all / ALWAYS / LAST in standard chain / MANDATORY"）成弹性措辞（"at least one / typically / skip when ..."）。这个方案即下一步该跑的 poc_precision，预期大概率能拿到 complex_04 / bilingual_01 类修复 同时保住 cr_* 主流链。

3. 对架构决策的影响——根 CLAUDE.md 里 "Sub-agent 解耦：每个 agent 自包含...互不依赖" 这条原则对 code 层（schema / evaluator / materializer 互不依赖）依然完全正确，但对 catalog 层（给 LLM 的自然语言描述）需要**降级为"尽量解耦，但允许点名邻居 agent 提供 scaffolding"——因为实验证明这是 LLM 路由的必要信息。纯粹的 capability card 形态不可行。

4. 两次实验合起来告诉我们的：catalog 里的 PascalCase 点名不是架构问题，是 prompt-engineering 必需品。真正要治的只有一类措辞——无出口的绝对量词。
